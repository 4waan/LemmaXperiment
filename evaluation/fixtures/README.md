# evaluation/fixtures/

Owner: operator, prepared in apparatus step 3 (EXPERIMENT.md section 4).
Public: the creator sees all of this. The held-out blocks are not here; their
selection rule and commitment are in `evaluation/holdout/` (step 4) and the
sealed manifest and salt are stored away from the creator.

Two fixture sets, one manifest each. The sha256 of a manifest is what the
demand and the evaluation policy pin.

## 1. Development corpus: `development-corpus.json`, `blocks/1/*.bin`

Three real mainnet blocks as the client inputs the pinned host produced for
them (bincode `ClientExecutorInput`: block, parent state tries, witness
nodes, bytecodes, ancestor headers). `apparatus-execute` with
`input_source=fixture` executes any of them offline after checking its sha256
against the manifest; the guest recomputes the post-state root and must reach
the header's `stateRoot`, so the expected output of every block is the header
two providers agree on.

| block | era | gasUsed | txs | cycles (standard) | input |
| --- | --- | ---: | ---: | ---: | ---: |
| 20600066 | Cancun | 958,960 | 27 | 22,629,229 | 437 KB |
| 18884864 | Shanghai | 4,266,500 | 30 | 89,571,800 | 1.7 MB |
| 23945771 | Osaka | 28,167,520 | 167 | 388,441,163 | 6.8 MB |

Provenance is in the manifest: run id, host binary hash, vkey, provider,
second-provider header check. No light client proves canonicality
(TRIE_MODULE_PROTOCOL.md section 8). Cycle totals move by about 0.01%
between executions of the same input (apparatus/INTERFACES.md section 7).

Regenerate the manifest after adding a block:
`RPC_1=... python3 corpus.py <block>=<apparatus/runs dir> ...`

## 2. Trie fixtures: `trie/fixtures.json`, `trie/gen.py`

Thirty-one cases (120 lookups, 11 update batches) at the `rsp_mpt::StateTries` seam, generated by `gen.py`
with py-trie 4.0.0 as the oracle (pure Python Merkle Patricia trie; it never
imports the Rust code under test). The file is deterministic for the seed;
`apparatus-fixtures.yml` regenerates it on every push and fails if a byte
differs, so the committed expectations are reproducible from the oracle.

Each case is a witness in EIP-1186 layout (per address: the RLP of every
hashed node from the state root along `keccak(address)`, and per storage slot
the same inside the storage trie; nodes shorter than 32 bytes are embedded in
their parent, never listed) plus what must happen:

- `expectedBuild`: `ok`, `reject`, or `ok-or-reject`;
- `queries`: account lookups expecting `present` (all four fields), `absent`
  or `reject`; storage lookups expecting a `value` (0x0 when unset) or
  `reject`. `reject` means an error or panic; an absent or zero answer where
  a rejection is required is a failure;
- `updates`: a `HashedPostState`-shaped batch (accounts to write or delete,
  storage slots to write or zero, wiped flags) with the state root and the
  storage roots py-trie computes after applying it, or `expect: reject`.

Families and what they cover (EXPERIMENT.md "Correctness",
TRIE_MODULE_PROTOCOL.md section 7):

| family | cases | covers |
| --- | ---: | --- |
| lookups | 5 | present keys; absent keys at every divergence point (root branch slot, extension mismatch at two depths, branch under an extension, leaf mismatch); empty trie; single-leaf root; inline leaves, an inline branch and an inline extension at depth 63; the 31/32-byte leaf boundary under one branch; two byte-identical storage tries; a consistent re-encoding with a changed leaf run right after the original (stale caches show) |
| missing-witness | 5 | partial witness (unrevealed paths must reject, never read absent); storage trie only as a root digest; dropped inner node; truncated paths; storage branch left out |
| incorrect-root | 3 | wrong declared state root; wrong declared storage hash; account leaf whose storage root disagrees with the supplied storage trie (the guest's storage-root check) |
| forged | 3 | leaf replaced with the chain broken; leaf replaced with every ancestor re-referenced but the original root declared; inline leaf forged inside its branch |
| malformed-rlp | 4 | truncated node; noncanonical long-form length prefix with the chain and root rebuilt consistently; branch carrying a value; two-item node with an empty path item |
| update | 11 | account rewrite; inserts that split a leaf and take an empty slot; delete with branch collapse, with and without the sibling resolved; storage rewrite, zeroing, insert and shrink across inline and hashed shapes; inline branch collapse into its inline extension; both leaves crossing the 31/32-byte boundary; wipe then write; delete an account with storage; create an account with storage; update through an unresolved path; write to one of two identical storage tries; code hash `null` |

Run order matters and is fixed (one process, file order): reordered and
repeated lookups are checked inside every case, and `a08` follows `a01` so a
cache that outlives a job would return the old leaf.

### Candidate-specific families

Two required families depend on the candidate's own representation and are
instantiated by the evaluator at evaluation time from the same cases:

- **forged handles**: whatever the candidate uses to refer to an
  authenticated node (an index, an offset, a pointer, a cache key) is
  altered in its encoded witness so that it points at a node never
  authenticated for that reference. Required outcome: the build or the
  lookup rejects, or the final root fails the state-root check; a value from
  the forged node must never be returned. For the seeded `arena` control the
  handle is the node index in the arena blob and the untrusted `psr`
  section (apparatus/INTERFACES.md section 4).
- **capacity boundaries**: the whole file is run once per cap setting, 0, 1,
  one below the selected cap and the cap itself (`lemma-fixtures --env
  KEY=VALUE` passes the setting). Required outcome: identical results across
  settings. Caps are correctness settings, chosen on the development corpus
  and frozen before holdout measurement.

## 3. Running the trie fixtures: `evaluation/harness/` (lemma-fixtures)

`apparatus-fixtures.yml` injects the harness into the pinned RSP workspace
as `bin/lemma-fixtures`, builds it against the unchanged pinned crates and
runs the file once per backend:

- `pointer`: upstream `EthereumState`, built with `EthereumState::from_proofs`
  (the host's construction from EIP-1186 proofs), then the guest's
  `build_trie_db` checks (state root, storage roots against account leaves),
  then the `StateTries` methods;
- `arena`: the same `EthereumState` re-encoded with `to_arena_witness` and
  decoded zero-copy with `ArenaTries::decode`, as the `arena` feature wires
  it (the seeded existing-capability control).

A candidate is run the same way once its `StateTries` implementation and
host encoder are in the workspace. Panics inside a backend are rejections
(they are in the guest). Results: `results-<backend>.json` per run with every
query and update outcome; the job fails on any mismatch.
